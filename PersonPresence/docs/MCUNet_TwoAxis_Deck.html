A 60-minute talk · 30 slides

MCUNet, on two axes

Every optimization in TinyNAS + TinyEngine attacks one of two scarcities.
This deck splits the project along that line and scores each technique.

SRAM ↓ cycles ↓
02 / 30 — Framing

The two scarcity axes

Every MCU deployment failure is a failure on one of these. MCUNet's optimization catalog maps cleanly onto them.

SRAM — the activation workspace

  • Hard ceiling, set by silicon
  • 128 KB – 1 MB on Cortex-M parts
  • Hit it → the program doesn't allocate
  • You can't trade average for peak

Cycles — the inference latency

  • Soft ceiling, set by clock + bus
  • 100 – 600 MHz on M4F / M7
  • Hit it → the program misses its frame
  • Every wasted cycle is dispatch, not math

The whole talk: Part A attacks the left column. Part B attacks the right.

03 / 30 — Why TFLM hits both ceilings

TFLM and the SRAM ceiling

  • Greedy arena — allocator can't see future tensor lifetimes
  • No in-place ops — every layer needs its own output buffer
  • No patching — full feature maps materialized in SRAM
  • Interpreter state sits in SRAM, alongside model metadata
04 / 30 — Why TFLM hits both ceilings

TFLM and the latency ceiling

  • Per-op dispatch — resolver lookup every layer, every frame
  • Generic kernels — branches on stride, padding, channels
  • Unknown loop bounds — compiler can't unroll or vectorize
  • Per-call requantization setup — multiplier table reads
PART A · 7 techniques

How MCUNet
cuts SRAM

Activations break the budget long before weights do. Every technique in this section reduces the peak activation footprint — the only number that matters when SRAM allocation fails.

A1 global memory schedule A2 in-place DWConv A3 patch inference A4 op reorder A5 static placement A6 no interpreter A7 TinyNAS-aware shapes
06 / 30 — A1 · TinyEngine

A1. Global memory scheduling

Compile-time bin-packing of buffer storage based on full-graph tensor lifetimes.

  • Mechanism — analyze graph → compute birth/death of each tensor → solve 2D packing offline
  • Why it works — non-overlapping lifetimes can share physical bytes (like register allocation)
  • Cost — codegen time only, zero runtime
  • Magnitude — 50–70% peak SRAM ↓ vs. greedy
  • Single largest source of TinyEngine's SRAM lead over TFLM
07 / 30 — A2 · TinyEngine

A2. In-place depthwise convolution

  • Mechanism — DW K×K reads small neighborhood, output written back into input buffer in raster order
  • Why it works — DW filters don't mix channels; spatial neighborhood is bounded → no read-write hazard
  • Magnitude — eliminates one full activation tensor per DW layer
  • Compounds with A1 — buffers freed earlier give the scheduler more reuse opportunities
  • This project has 18 in-place DW kernel variants on disk
08 / 30 — A3 · TinyEngine (MCUNetV2)

A3. Patch-based inference

  • Mechanism — depth-first per spatial patch instead of breadth-first per layer
  • Why it works — early CNN layers are spatially local; a patch + receptive-field margin computes independently
  • Magnitude — peak SRAM drops from full feature map to patch working set
  • Cost — small recompute at patch boundaries; V2 redistributes receptive fields to minimize overlap
  • Unlocks 320×320 input on parts that previously capped at ~144×144
09 / 30 — A4 · TinyEngine

A4. Operator reordering

  • Mechanism — when the graph has parallel branches, schedule them sequentially when no data dependency forces interleaving
  • Why it works — two branches "live at the same time" can be made non-overlapping in time
  • Cost — codegen time only
  • Magnitude — modest alone, compounds heavily with A1
  • Especially relevant for residual-block-heavy networks
10 / 30 — A5 · TinyEngine

A5. Static buffer placement

  • Mechanism — every buffer has a fixed address chosen at codegen time, emitted as buffer0[OFFSET]
  • Why it works — no runtime allocator → no metadata, no fragmentation, no padding for free-list overhead
  • Cost — rigidity; model swap = re-codegen + re-flash
  • Magnitude — modest standalone, but prerequisite for A1 and A4 to function
// genModel.c — what TinyEngine emits
static int8_t buffer0[PEAK_MEM] __attribute__((section(".dtcm")));

int8_t* getInput()  { return &buffer0[16384]; }
int8_t* getOutput() { return &buffer0[160]; }

/* every layer's input/output offsets baked in */
layer1_conv2d(buffer0 + 0,    buffer0 + 16384);
layer2_dw3x3 (buffer0 + 16384);              // in-place
layer3_pw1x1 (buffer0 + 16384, buffer0 + 0);  // reuse [0]
11 / 30 — A6 · TinyEngine

A6. No interpreter, no runtime structures

  • Mechanism — model is compiled-in C, not a data blob parsed at runtime
  • What goes away — FlatBuffer copy, OpResolver tables, MicroInterpreter state, per-tensor TfLiteTensor structs
  • SRAM angle — those structures live in SRAM on TFLM
  • Magnitude — single-digit KB on small models, low tens of KB on large ones
  • More of a latency win than SRAM win — see B1
12 / 30 — A7 · TinyNAS

A7. TinyNAS picks shapes that fit

  • Mechanism — NAS objective is accuracy subject to a hard SRAM constraint, queried by asking TinyEngine to schedule each candidate
  • Why it works — peak SRAM is not a smooth function of FLOPs or parameter count; only the engine knows
  • Cost — search-time cost only, offline
  • Magnitude — makes everything else tractable
  • Without A7 you'd need to hand-shape a network to fit the budget

15 / 30 — B1 + B2 · TinyEngine

B1. No interpreter · B2. No dispatch

// TFLM — every frame
for (op : flatbuffer_ops) {
  kernel = resolver.find(op.code);  // table lookup
  setup_tensors(op);                 // metadata read
  kernel.invoke(op.inputs, op.outputs);
}

// TinyEngine — generated once
void invoke() {
  layer1_conv2d_int8();                       // direct call
  layer2_dw3x3_stride1_inplace();
  layer3_pw1x1_int8();
  /* ... linker resolves these at build time ... */
}
  • B1 — no FlatBuffer parsing, no interpreter loop
  • B2 — no resolver lookup; kernel call sites are baked
  • Compiler can inline small kernels at the call site
  • Avoids i-cache miss on cold function-pointer dispatch
  • Magnitude — single-digit ms per frame across 50+ layers
16 / 30 — B3 · TinyEngine

B3. Compile-time loop bounds

Generic kernel

for (i = 0; i < out_h; i++)
  for (j = 0; j < out_w; j++)
    for (c = 0; c < out_c; c++)
      // bounds unknown
      // → no unroll
      // → no SIMD

Specialized kernel

for (i = 0; i < 32; i++)
  for (j = 0; j < 32; j++)
    for (c = 0; c < 96; c++)
      // fully unrollable
      // SMLAD/Helium fires
      // 2–4× faster
  • Mechanism — every layer's shape is known at codegen → bounds become literals
  • Magnitude — 2–4× on inner loops on Cortex-M4F / M7
  • Cost — flash size grows (each shape = its own kernel) — paid in plentiful flash
17 / 30 — B4 · TinyEngine

B4. Specialized per-shape kernels

  • Mechanism — separate .c file per (kernel size, stride, channel regime) combo
  • Why it works — generic kernels carry shape-dependent branches in the inner loop
  • Padding, dilation, requantization constants — all baked in
  • Cost — flash bytes only
  • Compounds with B3 to deliver the bulk of TinyEngine's per-layer speedup

18 / 30 — B5 · TinyEngine + CMSIS-DSP

B5. ARM SIMD intrinsics

  • Mechanism — packed-SIMD instructions on Cortex-M4F+
  • SMLAD — 2× 16-bit MAC per cycle (signed)
  • SMLALD — same, with 64-bit accumulator
  • Helium (M55, M85) — full vector instructions, ~8 int8 MACs/cycle
  • Magnitude — 2–4× vs. scalar code on the same MCU
19 / 30 — B6 · TinyEngine

B6. Layer fusion

  • Mechanism — Conv + BN + ReLU + (residual add) emitted as one kernel; BN folded into Conv weights
  • Why latency — 4 SRAM round-trips collapse to 1; intermediates stay in registers
  • SRAM bandwidth (AXIM) is the M7 bottleneck for many layers
  • Cost — debug granularity (no breakpoint between BN and ReLU)
  • Magnitude — 10–30% on bandwidth-bound layers
20 / 30 — B7 · TinyEngine

B7. Inlined requantization constants

  • Mechanism — int32 accumulator → int8 output requires multiplier × shift + zero-point
  • TFLM looks these up per layer, per call; TinyEngine bakes them as #define constants
  • Why it works — compiler emits immediate-mode instructions, skips per-call setup math
  • Cost — none
  • Magnitude — small per layer, accumulates to a couple percent end-to-end
// TFLM
quant_t* q = tensor->quantization;       // pointer chase
int32_t mult = q->output_multiplier;
int32_t shift = q->output_shift;
out = requantize(acc, mult, shift, zp);

// TinyEngine — emitted per layer
#define LAYER12_MULT 1374019256
#define LAYER12_SHIFT -7
#define LAYER12_ZP    -128
out = requantize(acc, LAYER12_MULT, LAYER12_SHIFT, LAYER12_ZP);
// → compiles to a single MUL + ASR + ADD on M7
21 / 30 — B8 · TinyEngine

B8. Cache-friendly memory layout

  • Mechanism — layout chosen per kernel, not globally
  • DWConv → CHW (channel-first) so each channel's H×W is contiguous
  • PWConv (1×1) → HWC so the channel axis (the contracted axis) streams
  • Transposes fused into the previous kernel where possible
  • Magnitude — single-digit to ~20% latency, more on parts with smaller D-cache
22 / 30 — B9 · Deployment

B9. DTCM placement of activation arena

  • Mechanism — Cortex-M7 has Tightly-Coupled Memory (DTCM/ITCM): dedicated bus, single-cycle, no cache
  • TinyEngine reports the exact PEAK_MEM; place that buffer in DTCM
  • Why it works — every kernel read/write bypasses AXIM and L1 D-cache
  • Cost — only on M7 / M55 / M85; M0/M3/M4 don't have DTCM
  • Magnitude — 1.5–3× on memory-bound kernels — single biggest deployment-time lever
// One linker-attributed line gets the whole win
static int8_t buffer0[PEAK_MEM]
    __attribute__((section(".dtcm")));

// linker.ld
.dtcm (NOLOAD) : {
    *(.dtcm)
} > DTCM            // 64KB single-cycle bank

If the activation arena fits in DTCM, every kernel's hot path becomes single-cycle. If not, fall back to SRAM.

23 / 30 — B10 · TinyNAS

B10. TinyNAS picks compute-efficient blocks

  • Mechanism — search over MBConv (mobile inverted bottleneck) blocks: expansion ratio, kernel size, depth, width
  • Cost function — accuracy at fixed FLOPs and fixed peak SRAM
  • Latency calibrated per-MCU from FLOPs
  • Magnitude — 3–5× FLOPs reduction from block family alone, +10–30% from configuration

Cross-cutting techniques

Three preconditions that enable everything in Part A and Part B.

C1. Static scheduling

Single-pass, codegen-time decision of everything — buffer offsets, kernel selection, op order.

SRAMcycles

Without this, A1, A4, B3, B4 cannot run.

C2. Per-channel int8 quant

int8 weights with per-channel scales, int8 activations with per-tensor scales — same scheme as TFLM-int8.

SRAMcycles

Halves the working set, enables packed-SIMD MACs.

C3. Co-design

TinyNAS searches "things TinyEngine can run efficiently" — TinyEngine optimizes "things TinyNAS produces."

both

The biggest meta-technique. Restricts the search space to the intersection.

28 / 30 — Case study · Tradeoffs

What we paid to get there

CostMagnitude
Flash weights190,864 B → 399,656 B (+109%)
Layer count70 → 51 (different topology)
Op coverageYOLO-style heads gone
Runtime model swapnot supported (re-flash)

Why the flash grew

Different model. TinyNAS gave VWW0 wider channels (up to 480) and 7×7 DW kernels because the input is small (64×64) — capacity has to go somewhere.

Classifier shape: narrow spatial, wide channels. Detector (YOLO) does the opposite.

On PIC32CZ-CA, flash is plentiful (4 MB) and SRAM is scarce — this trade is exactly right.

The flash growth is not a TinyEngine artifact — it's the model. Apples-to-apples on the same network, weights are ~equal.

29 / 30 — Decision rule

When to pick MCUNet, when to stay with TFLM

Pick MCUNet when

  • SRAM is the binding constraint
  • Latency target is hard (FPS / real-time)
  • Model is locked-down for shipping
  • MobileNet-shaped network

Stay with TFLM when

  • You need runtime model swap
  • SRAM isn't the bottleneck
  • Network uses exotic / custom ops
