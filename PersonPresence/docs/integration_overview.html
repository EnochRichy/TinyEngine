What is TinyEngine?

A memory-efficient inference library from MIT Han Lab, co-designed with the MCUNet neural-architecture search. It schedules memory by overall network topology — not layer-by-layer — and emits flat C source instead of running an interpreter.

Co-designed with MCUNet

TinyNAS searches an efficient architecture; TinyEngine compiles it to MCU-class C. Joint optimization beats either piece alone.

Static memory plan

No malloc, no runtime planner, no interpreter. The codegen emits one buffer, one schedule, one straight-line invoke().

Source-level codegen

Generates plain C kernels with the model already specialized — channel counts, kernel sizes, strides, scales are all compile-time constants.

Profiled on STM32H743 against TFLite-Micro, CMSIS-NN, and X-CUBE-AI for the same MCUNet-VWW0 net (numbers from the upstream TinyEngine README):

Metric (mcunet-vww0) TFLite-Micro CMSIS-NN X-CUBE-AI v7.3 TinyEngine
Latency 587 ms 53 ms 32 ms 27 ms
Peak SRAM 163 kB 163 kB 88 kB 59 kB
Flash weights 627 kB 646 kB 463 kB 453 kB
Across the MCUNet model family: 1.1×–18.6× faster and 1.3×–3.6× lower peak memory than the next-best.
03

Optimization techniques

The seven tricks that let TinyEngine run a 51-layer MobileNetV2-style net in 60 KB of SRAM. All are baked into the generated kernels — there's no runtime cost to "enable" them.

In-place depthwise conv

Depthwise reads and writes the same channel — overlap input/output buffers and save the activation memory entirely.

Patch-based inference

For early layers (memory-bottleneck stage), process spatial patches with overlap rather than the full feature map. Up to 8× peak-memory drop on MobileNetV2.

Operator fusion

Conv + bias + ReLU + requantize collapse into one kernel — single pass over the data, no intermediate tensor written to memory.

Im2col GEMM

Convolution lowered to a matrix multiply against a column-formatted patch buffer. Maps cleanly to the SIMD MAC pipeline.

SIMD packing

Four int8 multiply-accumulates per cycle on Cortex-M with DSP extensions. Weights are reordered at codegen time to match.

HWC → CHW transform

Weights are laid out in CHW for in-place depthwise so each channel's read/write region is contiguous — better cache behaviour.

Loop reorder / unroll / tile

Per-kernel loop nest is hand-tuned at codegen time for the specific (kH, kW, stride, channels) tuple — 18 depthwise variants emitted for VWW0 alone.

One static arena

All activations share a single buffer0[] with offsets chosen at codegen time. Live ranges of tensors are packed; no dynamic allocator is linked.

The MCUNet-VWW0 model

Net id mcunet-10fps_vww from the MCUNet zoo. A 2-class person/no-person classifier — the smallest of the three VWW variants, designed for ~10 FPS on a Cortex-M7.

Tensor shapes

/* read from .tflite, not derived */
input  : [1, 64, 64, 3]  // HWC int8
output : [1, 2]          // [no-person, person]
layers : 51
weights: 399 656 B (flash)
arena  : 60 800  B (SRAM)

Quantization params

/* input — pixels normalized to ~[-1,1] */
scale = 0.00784314
zp    = -1

/* output — real logit = q × scale */
scale = 0.09819
zp    = 0
// margin 35 → 3.44 → ~97% softmax

Layer stack — 64×64×3 collapses through 51 layers down to 1×1×2

Spatial dim shrinks (stride-2 depthwise every few blocks); channel count grows then collapses through global-avg-pool to the 2-logit classifier head.

Generating the model code

From a pretrained .tflite in the MCUNet model zoo to a tree of plain C source you compile into your firmware. Four commands, no PyTorch dependency at codegen time.

1 · Pick the net

Edit tinysrc/examples/vww.py line 25 to set the net id. For VWW0:

net_id = 'mcunet-vww0'

2 · Fetch the tflite

Drop the file into tinysrc/assets/ manually (avoids the torch dependency in download_tflite()):

# from hanlab18.mit.edu/projects/tinyml/mcunet/release/
mcunet-10fps_vww.tflite  → tinysrc/assets/

3 · Run codegen

Generates the full C model into tinysrc/codegen/{Include,Source}/:

cd tinysrc
python -c "from code_generator.CodegenUtilTFlite \
  import GenerateSourceFilesFromTFlite; \
  GenerateSourceFilesFromTFlite( \
    'assets/mcunet-10fps_vww.tflite', \
    life_cycle_path='./lifecycle.png')"

4 · Drop into the project

Copy the two output dirs into the firmware tree:

cp -r codegen/Include codegen/Source \
   ../PersonPresence/My_MCC_Config/src/TinyEngine/codegen/

What it emits

A 51-layer flat invoke(), the activation arena, all weight blobs as const arrays, and one .c per depthwise variant the network actually uses. For VWW0 that's 18 depthwise kernel files — the cross product of:

3 × 3 · 5 × 5 · 7 × 7

kernel sizes

stride 1 · stride 2

spatial reductions

plain · mask · bitmask

channel-mask variants

Click to expand: annotated genModel.c excerpt — first 12 layers

Note how every call writes into a fixed offset of the single buffer0[] arena. Yellow lines are the public entry points. There is no malloc, no graph object, no scheduler at runtime — this is the schedule.

signed char* getInput() { return &buffer0[16384]; }
signed char* getOutput() { return NNoutput; }   // = &buffer0[160]

void invoke(float* labels) {
/* layer 0 : CONV_2D — 64×64×3 → 32×32×16 (stride 2) */
  convolve_s8_kernel3_inputch3_stride2_pad1_fpreq(
      &buffer0[16384], 64,64,3,
      (const q7_t*) weight0, bias0, scales0,
      -128,1,-128,127,
      &buffer0[0], 32,32,16, sbuf, kbuf, -1);

/* layer 1 : DEPTHWISE_CONV_2D — in-place 3×3 stride-1 */
  depthwise_kernel3x3_stride1_inplace_CHW_fpreq(
      &buffer0[0], 32,32,16,
      (const q7_t*) CHWweight1, offsetBias1, offsetRBias1, scales1,
      -128,128,-128,127,
      &buffer0[0], 32,32,16, sbuf, -128);   // in == out

/* layer 2 : CONV_2D 1×1 — 16ch → 8ch (squeeze) */
  convolve_1x1_s8_ch16_fpreq(&buffer0[0], …, &buffer0[49152], 32,32,8, sbuf);

/* layer 3 : CONV_2D 1×1 — 8ch → 48ch (expand) */
  convolve_1x1_s8_ch8_fpreq(&buffer0[49152], …, &buffer0[0], 32,32,48, sbuf);

/* layer 4 : DEPTHWISE 5×5 stride 2 — spatial 32→16, in-place */
  depthwise_kernel5x5_stride2_inplace_CHW_fpreq(&buffer0[0], 32,32,48, …,
      &buffer0[0], 16,16,48, sbuf, -128);

/* layers 5-7 : project / expand / depthwise — inverted residual block */
  convolve_1x1_s8_ch48_fpreq( …, &buffer0[16384], 16,16,16, …);
  convolve_1x1_s8_ch16_fpreq(&buffer0[16384], …, &buffer0[0], 16,16,64, …);
  depthwise_kernel3x3_stride1_inplace_CHW_fpreq(&buffer0[0], …);

/* layer 8 : 1×1 conv — write into a *different* slot to set up the residual ADD */
  convolve_1x1_s8_fpreq( …, &buffer0[20480], 16,16,16, sbuf);

/* layer 9 : ADD — fused requantize, two int8 inputs, one int8 output */
  add_fpreq(4096,
      &buffer0[20480], 0.0705844, 6,    // scale + zp of input A
      &buffer0[16384], 0.0849132, -22,  // scale + zp of input B
      0.0940756, -7,                          // scale + zp of output
      &buffer0[24576]);

  /* … 41 more layers, ending in a 1×1×2 logit tensor at &buffer0[160] */
}
06

Memory layout

Two static regions, both fixed at link time. The SRAM arena is the single buffer all activations time-share. Flash holds the weight blobs as const arrays.

Why so small?

In-place depthwise lets layer 1's input and output occupy the same 16 KB slot. Without it, peak SRAM would roughly double.

Why is flash bigger than the old detector's?

NAS for VWW0 spends its budget on channel width (up to 480 ch, 7×7 depthwise) instead of spatial size. Classifier shape — flash-cheap MCUs win, SRAM-cheap MCUs lose.

76% SRAM cut vs the old YOLO detector

Old person-det: 257 448 B SRAM, 190 864 B flash, ~330 ms. VWW0: 60 800 B SRAM, 399 656 B flash, <70 ms. SRAM is the binding constraint on PIC32CZ-CA, so the trade is correct.

07

MCU integration · per-frame flow

Two cooperating Harmony state machines — APP_CAM_Tasks drives the camera, APP_ML_Tasks drives inference. They synchronise via a single flag, processed_frame_data_ready.

1 · Capture (DMA, no CPU)

OV7670 streams RGB565 over the parallel bus → PCC (Parallel Capture Controller) → DMA → panda_scaled_data[160·120·2]. The VSYNC ISR sets processed_frame_data_ready = true.

2 · Preprocess

rgb565_to_modelinput_vww() in app_cam.c center-crops 160×120 → 120×120, bilinearly resizes to 64×64, decodes RGB565 to RGB888, and writes int8 = uint8 - 128 directly into getInput().

3 · Inference

signed char* in = getInput();      // &buffer0[16384]
rgb565_to_modelinput_vww(frame, in);
invoke(NULL);                       // run the 51-layer graph
signed char* out = getOutput();    // 2× int8 logits

4 · Decision

out[0] = no-person, out[1] = person (alphabetical class order — matches torchvision.ImageFolder and MCUNet's eval_tflite.py). Margin = out[1] - out[0] in int8 units.

5 · EMA + asymmetric hysteresis

Raw argmax flickers when logits straddle zero. We low-pass the margin (α = ¼ ≈ 3-frame TC at 15 FPS) and apply different enter/exit thresholds. Brief drops (head-turn, single bad frame) don't lose a detected person.

/* in app_ml.cpp */
#define PERSON_EMA_ALPHA_SHIFT  2             // alpha = 1/4
#define PERSON_ENTER_Q8         ( 4 * 256)   // flip ON when smoothed margin ≥ +4
#define PERSON_EXIT_Q8          (-8 * 256)   // flip OFF when smoothed margin ≤ -8

s_margin_ema_q8 += (raw_q8 - s_margin_ema_q8) >> PERSON_EMA_ALPHA_SHIFT;
if (!s_person_present && s_margin_ema_q8 >= PERSON_ENTER_Q8) s_person_present = true;
else if ( s_person_present && s_margin_ema_q8 <= PERSON_EXIT_Q8 ) s_person_present = false;

6 · USB CDC dashboard

16-byte header (magic + frame counter + decision + margin + inference µs) followed by the raw 160×120 RGB565 frame. Python Dashboard_via_USB.py shows live frame, decision badge, logit margin, inference time and FPS.

08

Verification harnesses

Three independent ways to test the same firmware — synthetic inputs prove the kernels are wired correctly, baked images prove the model is healthy, the live dashboard proves the camera path is sane.

Smoke test

APP_ML_RunSmokeTest() invokes the model on three synthetic constant inputs (mid-grey, all-black, all-white) and prints the resulting logits over UART. Confirms the kernels link, run to completion, and produce numerically distinct outputs for distinct inputs.

midgray → [+a, -a]
black   → [+b, -b]
white   → [+c, -c]

Image test (ground truth)

Set ML_USE_TEST_IMAGES = 1 in app_ml.h, rebuild and flash. APP_ML_RunImageTest() bypasses the camera and feeds 6 pre-baked 64×64×3 int8 images from test_images.h through invoke(), reporting PASS/FAIL.

Live dashboard

Dashboard_via_USB.py over USB CDC. Shows the live RGB565 frame, decision badge (person / no-person), live logit margin, per-frame inference time and rolling FPS. The "real" verification — closes the loop end-to-end through the camera.
