03 / 33 — The memory wall

Why activations break the budget

  • Weights live in flash — cheap, abundant
  • Activations live in SRAM — scarce, expensive
  • One 160×160×16 int8 feature map = 409,600 B
  • Already over budget on a 256 KB-SRAM part
  • Model fits. The workspace doesn't.

The math, plainly

H × W × C × bytes
160 × 160 × 16 × 1
= 409,600 B  ≈ 400 KB

256 KB SRAM part →  FAIL
512 KB SRAM part →  78% just for one tensor
1 MB SRAM part   →  ~40% — and that's one layer
04 / 33 — TFLM refresher

TFLM at a glance

You know this. We're only here for the overhead it implies.

  • Portable — drop in a new .tflite
  • Generic — single binary, many models
  • Easy deployment, big op coverage
  • One runtime to maintain
  • None of this is free.
05 / 33 — TFLM refresher

Where TFLM leaves performance on the table

  • Per-invocation dispatch — operator resolver looks up a kernel every layer, every frame
  • Greedy arena — allocator can't see future tensor lifetimes
  • Generic kernels — runtime branching on stride / channels / padding
  • Resolver tables — flash and cycles spent on machinery, not math

none of these are bugs they are the cost of being a general runtime — exactly the cost TinyEngine sets out to avoid.

07 / 33 — The shift

Code-generation, not interpretation

  • Input: a quantized .tflite file
  • Output: straight-line C — one function call per layer
  • No interpreter, no resolver, no FlatBuffer parsing at runtime
  • The "engine" is the generator; what runs on the MCU is just C

void invoke(void) {

    layer3_conv1x1_int8();

}

12 / 33 — Execution model

What this buys, what it costs

Buys

  • Lower latency — no dispatch indirection
  • Smaller flash — no interpreter logic
  • Compiler can inline constants
  • Cross-op optimization fires
  • Predictable WCET, easier to bound

Costs

  • Re-codegen + re-flash to swap models
  • No runtime model loading from FS
  • Smaller op coverage than TFLM
  • Tooling/community is smaller
  • Debug across many specialized kernels

A deliberate trade — and the right one when SRAM is the binding constraint.

13 / 33 — Optimization 1 of 6

Global memory scheduling

  • Full-graph lifetime view → like register allocation
  • Two tensors, non-overlapping lifetimes → share storage
  • Solved at compile time, not runtime
  • Quoted MCUNet result: 50–70% peak-SRAM reduction vs. greedy
14 / 33 — Optimization 2 of 6

In-place depthwise convolution

  • DW K×K reads a small spatial neighborhood
  • One output per channel, locally bounded write
  • Output overwrites input as we go
  • Saves one whole activation tensor per DW layer
  • Huge win for MobileNet-class bottlenecks
15 / 33 — Optimization 3 of 6

Patch-based inference

  • Run a spatial patch through several layers depth-first
  • Move to next patch, repeat
  • Never materialize the full early feature map
  • Unlocks 320×320 input on small SRAM parts
  • Tradeoff: small recompute at patch boundaries
16 / 33 — Optimization 4 of 6

Layer fusion

  • Conv + BN + ReLU + (optional residual add) → one kernel pass
  • Single sweep through SRAM, single i-cache load
  • TFLM fuses activation. TinyEngine fuses across the pre-quant sequence.
  • Wins on memory bandwidth — often the M7 bottleneck
17 / 33 — Optimization 5 of 6

Static scheduling, specialized kernels

  • No virtual dispatch, no function pointers
  • Compiler sees concrete loop bounds → aggressive unrolling
  • Zero runtime shape / stride checks in the inner loop
  • SIMD MAC (SMLAD / SMLALD on M4F+, Helium on M55) actually fires

What the compiler sees

// generic (TFLM-style)
for (i = 0; i < out_h; i++)
  for (j = 0; j < out_w; j++)
    for (c = 0; c < out_c; c++)
      /* bounds unknown → no unroll */

// specialized (TinyEngine)
for (i = 0; i < 32; i++)
  for (j = 0; j < 32; j++)
    for (c = 0; c < 96; c++)
      /* fully unrollable, vectorizable */
18 / 33 — Optimization 6 of 6

Quantization plumbing

  • int8 weights with per-channel scales — same as TFLM-int8
  • int8 activations with per-tensor scales
  • Fixed-point requantization — the _fpreq suffix in kernel filenames
  • Multipliers and shifts inlined per-layer at codegen time
  • No runtime table lookup, no per-call setup math

numerical compatibility Same int8 outputs as TFLM — TinyEngine doesn't change the math, it changes when the constants get baked.

20 / 33 — Memory planner deep-dive

Greedy vs. global allocation

Greedy (TFLM-style)

L1: alloc T1 → 32 KB
L2: T1 alive, alloc T2 → 64 KB peak
L3: T2 alive, alloc T3 → 48 KB
L4: T3 alive, alloc T4 → 24 KB
64 KB peak

Global (TinyEngine)

L1: alloc T1 at 0x00 → 32 KB
L2: alloc T2 at 0x20 → 40 KB peak
L3: T1 dead → T3 reuses 0x00
L4: T2 dead → T4 reuses 0x20
40 KB peak (−37%)

Same model, same numerics, less SRAM. This is the single biggest source of TinyEngine's memory advantage.

23 / 33 — Cortex-M7 walkthrough

Mapping layers to memory on Cortex-M7

  • Weights → flash — they don't need to be fast
  • Activation arena → DTCM — single biggest M7 latency lever
  • Input/output → SRAM — DMA-friendly
  • One __attribute__((section(".dtcm"))) on the arena buffer
  • TinyEngine tells you the exact PEAK_MEM at codegen time

25 / 33 — Deployment

What you actually link in

  • genModel.c + weights.c
  • Only the kernel .c files your network calls
  • CMSIS-Core, optionally CMSIS-DSP
  • No TFLM library, no FlatBuffers library, no resolver

Footprint comparison

TFLM runtime + ops~80–120 KB flash
TinyEngine kernels (only used)~15–30 KB flash

If you don't use MaxPool, MaxPool code never gets compiled or linked. There is nothing to dead-strip — it was never there.

30 / 33 — When NOT to pick TinyEngine

Honest tradeoffs

  • Op coverage is narrower than TFLM — exotic ops may not generate cleanly
  • Model swap requires re-codegen + re-flash — no field-side .tflite drop-in
  • Tooling and community are smaller than TFLM
  • Debugging across many specialized kernel variants is more work

Stay with TFLM when

  • SRAM is not the bottleneck
  • You need runtime model swap
  • Network is exotic / experimental

Pick TinyEngine when

  • You're SRAM-bound on a known model
  • Latency is a hard requirement
  • The model is locked-down for shipping
31 / 33 — Roadmap

Future directions

MCUNetV2

Improved patch-based inference — receptive-field redistribution to reduce overlap recompute, larger inputs at lower SRAM cost.

MCUNetV3

On-device tiny training. Sparse update, quantized backprop on MCU. Personalization at the edge without re-flashing.

The broader trend

As model shapes stabilize around MBConv / DWConv primitives, generated runtimes win over generic ones. Edge-AI follows the same path embedded compilers did.

32 / 33 — Wrap-up

Key takeaways

  • TinyEngine is a code generator, not a runtime — it removes the interpreter, not the math
  • Global memory scheduling is the single largest SRAM win
  • In-place DWConv + fusion + static scheduling compound the win on MobileNet-class nets
  • Patch inference unlocks larger inputs on small SRAM
  • For TFLM-native engineers: integration is "drop generated C in, call invoke()"
